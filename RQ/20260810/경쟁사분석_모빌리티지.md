## 1. 기능 대조

### 1-1. 우리가 이미 가진 것 (도입 불필요 — 다시 제안하지 말 것)

| 경쟁사 기능 | buslink 현황 |
|---|---|
| 실시간 차량 위치·지도/리스트 전환 | 승객앱·직원앱·관제·협력사 포털 4화면 |
| 정류장 타임라인·통과 표시 | 노선도 스트립 + 요약 진척바 |
| 도착 예정시간 안내 | `computeStopEstimates` chain plan-first + 진척률 안분 |
| 도착 임박 알림 | `notifyPreArrival` + 시간표 폴백 `notifyPreArrivalBySchedule` |
| QR 탑승(카메라 인식) | 동적 QR·정적 QR·승객 발행 QR **3종** + jsQR 인앱 스캐너 |
| 로드뷰 | EmployeeApp 정류장 카드·노선 탭(`Roadview radius:60`) |
| 관리자 실시간 관제·궤적·속도 | MapTab + 운행 이력 |
| 정류장 도착/미도착/조기출발 | `stopArrivals` + `delaySec` + 노선도 뷰 |
| 운행 강제 종료 | 2026-07-28 잔존 신호 정리 + 강제 종료 버튼 |
| 운행 기록 캘린더 | HistoryTab(일자별·궤적·반경 시각화) |
| 메시지/공지 발송(노선별·개인별·예약발송) | `sendNotice` + 협력사 발송 + 강제 공지 모달 |
| 노선 생성·경로 사전 확인 | 노선 관리 + `routePath` 수동 그리기 + `getNaviRoute` 도로 경로 |
| 출근/퇴근 색 구분 | `type === '출근'` 파랑 / 그 외 오렌지 (EmployeeApp 3곳) |
| 고객사 브랜딩 | `partnerCodes.branding`(컬러·로고, CSS 변수 덮어쓰기) |
| 승·하차 태그 인프라 | NFC 사원증(`boardNfc`)까지 있음 — 저쪽엔 **없다** |

> **NFC 사원증 탑승은 우리만 있다.** 경쟁사 탑승 수단은 태그리스·QR 둘뿐이다. 기존 사원증 재사용이 가능한 고객사에는 이게 우리 쪽 우위다.

## 2. 도입 권고

### 🟢 지금 하면 좋은 것 (저비용·체감 큼)

**① 헬프 오버레이 (E)** — 가장 싸고 가장 효과적이다.
경쟁사가 헬프에 넣은 4개 중 하나가 **"노선이 화면에 안 나오는 경우"**다. 우리가 겪는 신고 1순위와 정확히 같은 문제(운행 시간창 밖·노선 미등록·거래처 미배정). 우리는 이미 화면에 이유를 쓰고 있지만(`19:20~22:20에 운행 정보가 표시됩니다`), **묻기 전에 답을 주는 통로**가 없다. 상단 `?` 버튼 + 3~4장 캐러셀이면 된다. 프론트 전용·백엔드 0.

**② 알림 설정 화면 (D)** — 우리 최대 병목과 직결된다.
`tasks.md` 에 적어 둔 대로 **'내 정류장' 지정자가 5명**이라 트리거를 100% 고쳐도 도달 인원이 5명에 묶인다. 경쟁사는 알림을 **일급 화면**으로 올려 사용자가 알림을 "설정하러 들어오게" 만든다. 우리도 설정 탭의 진단 카드 옆에 알림 설정 섹션을 두고, 그 안에서 **내 정류장 지정을 유도**하면 지정률이 오른다. 시간대별 토글까지는 과할 수 있으나 **출근/퇴근 알림 분리 + 하차 정류장 알림**은 통근버스 문맥에 맞다.

**③ 로드뷰 지점 지정 (G)** — 지금 조용히 틀리고 있을 수 있다.
우리 로드뷰는 정류장 좌표 반경 60m 최근접 파노라마를 자동으로 잡는다. 왕복 노선에서 **반대 차선 파노라마가 잡히면 승객이 길 건너에서 기다린다.** 경쟁사가 "상·하행 혼동 없이"를 명시적으로 내세우는 이유가 이것이다. 조치 = `stops` 에 `roadviewPanoId`/`roadviewPan` 선택 필드 추가 + 관리자 정류장 편집에서 지정. **먼저 실측할 것** — prod 정류장 206개 중 몇 개가 반대 차선을 잡는지부터 세고, 유의미할 때만 착수.

**④ 시간표 화면 (F)** — 데이터는 이미 다 있다(`departTime` 전 노선 보유 + `offsetMin` 87%). 읽기 전용 그리드 한 장.

### 🟡 검토 후 결정

**⑤ 태그리스 (B)** — 이게 제일 흥미롭다.
우리 부품이 이미 다 있다: GPS 근접 판정(승객앱 proximity 오버레이), boarding 생성, 멱등 doc id `${empNo}__${vehicleId}`. **새로 만들 것은 "근처에 오면 버튼이 뜬다"는 표시 규칙과 승차권 카드 한 장뿐**이다.
- **장점**: QR 스캔(카메라 켜고 조준)·NFC(폰을 대야 함)보다 마찰이 낮다. 비 오는 날·양손에 짐 있을 때 차이가 크다.
- **🔴 단점(정직하게)**: 승차권은 **기사가 눈으로 보는 것**이라 탑승 데이터의 신뢰도가 QR·NFC보다 낮다. 안 누르고 타는 사람, 눌러놓고 안 타는 사람이 생긴다. 우리 탑승 통계·정류장 매핑은 지금 **실제 태깅 기반**이라 정확한데, 태그리스를 섞으면 그 정확도가 내려간다.
- **권고**: 태그리스를 **QR·NFC 대체가 아니라 4번째 모드로 추가**하고, `boardings.via:"tagless"` 로 구분해 통계에서 갈라 볼 수 있게. 어느 모드를 쓸지는 **거래처별 옵션**(`boardingMode` 선례 그대로).

**⑥ 좌석 예약 실물 (C)** — 스위치는 이미 prod 에 있고 켠 거래처가 0곳이다.
경쟁사 화면 4장이 **그대로 우리 스펙**이 된다: 캘린더 다중 날짜 → 좌석 배치도(28인승·출입구 표시·선택가능/불가 범례) → 확인 카드(노선·출발·도착·좌석번호·운행시간) → 예약내역/취소. 만들기 전에 **고객사가 켜겠다고 해야** 한다(그래서 스위치만 먼저 냈다). 결제는 여전히 불필요 — 통근버스는 회사 부담이고, 저쪽도 "결제 시 건당 수수료 발생"이라 스스로 적어 뒀다.

**⑦ 고객사 전용 앱 (H)** — PWA 라 **중간 지점이 있다**. 거래처별 `manifest` 를 갈아 끼우면 홈 화면 아이콘·이름·스플래시가 그 회사 것이 된다(우리는 이미 앱별 manifest 3종을 운영 중이라 확장 경로가 열려 있다). 네이티브 스토어 앱까지 갈 필요는 없다.

### 🔴 큰 트랙 — 별도 판단

**⑧ 클러스터러 (A)** — **유일한 진짜 기능 갭이고, 성격이 다르다.**
이건 운행 관리 기능이 아니라 **영업 도구**다. "임직원 주소 주시면 노선을 설계해 드립니다"가 되는 순간 제안의 성격이 바뀐다. 신규 고객사 온보딩에서 가장 아픈 지점(정류장을 어디에 둘까)을 우리가 대신 풀어준다.
- 필요한 것: 주소 엑셀 업로드 → 지오코딩(카카오 Geocoder 보유) → 지도 클러스터 표시 → 정류장 후보 제안.
- 🔴 **주의**: 임직원 집 주소는 **민감 개인정보**다. 저장하지 말고(업로드 → 좌표 변환 → 집계 → 원본 폐기), 화면엔 개별 핀이 아니라 **집계 버블만** 띄워야 한다. 경쟁사 화면도 버블(숫자)만 보인다.
- way 판단 필요: 영업 도구에 개발 리소스를 쓸 시점인가.

**⑨ 보안 인증 (I)** — 두 갈래고 무게가 다르다.
- **Observatory / Qualys 등급**: 싸다. Firebase Hosting 이라 SSL 등급은 이미 좋을 것이고, CSP·HSTS 헤더 몇 줄이면 A 대 등급이 나온다. 제안서에 붙일 배지 한 장 값으로 저렴.
- 🔴 **위치기반서비스사업자 신고**: 이건 기술이 아니라 **법률 확인 사항**이다. buslink 는 차량 위치를 수집해 고객사(제3자)에게 보여주는 구조라 위치정보법상 신고 대상일 가능성이 있다. 경쟁사가 신고필증을 제안서 앞에 내건 건 그게 **입찰 요건이 되는 경우가 있어서**다. **내가 판단할 사안이 아니다 — way 가 법무/행정 확인 필요.** 미신고 상태로 대기업 입찰에 들어가면 서류에서 걸릴 수 있다.

### ⬜ 도입하지 말 것

**⑩ 자가 회원가입 (J)** — 2026-07-27 에 이미 결론 났다(고정 명부 + 담당자 셋팅이 운영 현실, 동명이인·외부인 유입 위험). 경쟁사가 한다고 뒤집을 이유가 없다. 대신 우리는 **계정 안내문 인쇄 + QR 프리필**로 배부 마찰을 이미 풀었다 — 이쪽이 통근버스 문맥엔 더 맞다.

**⑪ AI QR** — 이름만 AI다. "카메라가 QR 만 인식해 스치기만 해도 태그"는 우리 jsQR 인앱 스캐너가 하는 일과 같다.

### 3-1. 앱 화면

| 요소 | 경쟁사 방식 | 우리에게 |

| **FAB (+)** | 예약 화면 우하단 파란 원형 + 말풍선 코치마크(`이곳을 눌러 탑승 예약을 할 수 있어요`) | **코치마크가 좋다.** 새 기능을 내면 첫 진입 1회 말풍선으로 짚어주는 패턴 |
| **상태 배지** | `탑승완료`/`미탑승` 필터 칩 + 상태 텍스트 | 우리 필터 칩과 동급 |

### 3-2. 제안서 자체 (우리 매뉴얼·제안서에 반영)

우리 `docs/manual/` 산출물과 비교해 **가져올 만한 편집 문법**:

- **섹션 표지**: 큰 파란 숫자 + 국문 제목 + 영문 부제. 23쪽짜리를 3덩어리로 잘라 읽는 부담을 낮춘다.
- **파란 띠 요약 박스**: 모든 본문 쪽이 제목 아래 **파란 그라데이션 박스 안 bullet 2~3줄**로 시작한다. 쪽마다 형식이 같아서 훑기 쉽다. 우리 매뉴얼은 이 일관된 진입 블록이 없다.
- **폰 목업 가로 나열**: 화면 4~5개를 **왼→오 흐름 순서**로 늘어놓아 "무엇을 순서대로 하는지"가 그림만으로 읽힌다. 회색 바닥 띠가 폰을 세워 보이게 한다.
- **관리자 기능은 데스크톱 목업 1장**: 화면을 쪼개 설명하지 않고 통째로 보여주고 위 bullet 로 요점만. 관리자 화면은 원래 복잡하니 이 편이 정직하다.
- **마지막 장 = 고객사 로고 그리드**: 25개사 5×5. 기능 20쪽보다 이 한 장이 세다.

> ⚠️ 원본이 **스캔본이라 화질이 나쁘다**(글자 뭉개짐·회색 얼룩). 편집 문법만 참고하고 **품질은 우리가 더 낫게** 만들 수 있다 — 우리는 Playwright 로 실제 화면을 캡처해 PDF 를 만든다.

## 4. 진짜 격차 (기능이 아니다)

마지막 장이 이 제안서의 결론이다 — **쿠팡·카카오·무의한형제들·NOL UNIVERSE·kt ds·셀트리온·GC녹십자·JW중외제약·LX Semicon·신성E&G·경신·다산네트웍스·모트렉스·S Traffic·YMC·수흥·TENERGY·PENTA스퀘어·PAYCO·INNOX·곤지암리조트·제로쿨투어·하나·가나투어·서울고속관광.**

기능 표로 이길 수 있어도 **레퍼런스 표로는 지금 못 이긴다.** 우리가 가진 것은 동영관광 자사 운영 + 채드윅송도국제학교(승객 245명) + 신촌세브란스 등 9개 거래처다. 대신 우리에겐 저쪽에 없는 것이 있다 —
**① 자사 운수회사 운영 경험**(우리가 직접 버스를 굴린다) ②**NFC 사원증** ③**요청 대응 속도**(개선요청 게시판 → 당일 배포가 실제로 돌아간다).

제안서를 만든다면 기능 나열이 아니라 **이 세 가지로 프레임을 잡는 게** 정면 대결보다 낫다.
